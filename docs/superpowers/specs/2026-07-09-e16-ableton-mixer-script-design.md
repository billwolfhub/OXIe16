# OXI e16 Ableton Live 12 Mixer Script — Design

## Goal

Port the mixer functionality of an existing Midi Fighter Twister Ableton Live control
surface script (generated by Remotify/Control Surface Studio, `MFT script from remotify/css_bw43/`)
to a hand-written Ableton Live 12 Remote Script for the OXI e16.

## Scope

- Encoders 1–16 → absolute Track Volume, tracks 1–16 (fixed window, first 16 visible tracks, no bank-scrolling)
- Encoder-push buttons 1–16 → Track Mute toggle, tracks 1–16
- Bidirectional LED feedback: Ableton-side volume/mute changes (mouse, automation, project load) push CC/Note back to the e16 so its ring position and button LED stay in sync
- Ableton Live 12 only. No Bitwig, no sends, no shift/bank layer — the Twister script has an unused "mode 2" (send) and "shift mode" layer, but the user only uses volume + mute, so those are dropped, not ported.

Out of scope (v1): the e16's SysEx-based "remote mode" protocol (custom RGB per-LED,
bipolar ring rendering, OLED framebuffer/text labels) documented in
`Misc from OXI/OXI REMOTE.xlsx`. Only pursue this as a phase 2 if the plain-CC version
falls short visually.

## Hardware configuration

Per `Misc from OXI/OXI REMOTE.xlsx` (E16 sheet), the e16's native/default MIDI behavior
already matches what this script needs — no custom on-device SysEx scripting required:

- Encoders send/receive absolute CC, channel 1 (0-indexed channel 0), CC numbers 1–16
- Encoder-push buttons send/receive Note on/off, channel 1, notes 0–15
  (note: CC number = encoder index + 1, so encoder *n* uses CC *n*; its push button uses note *n-1*)

This behavior lives in an on-device **scene**, configured and saved via the OXI desktop
app — the same mechanism the reference Bitwig script relies on (it ships a
`Bitwig.oxie16` scene file and its README documents exactly this: set knobs to `Absolute
CC` mode, drag the scene onto an **On Device** slot to persist it, reboot to clear
cache). It is not yet known which scene is currently active on this hardware or whether
it already matches the required layout.

Action item before writing code: probe the hardware's actual raw MIDI output (not just
trust the spreadsheet), and if it doesn't match, build and save a scene via the OXI
desktop app that does. Also confirm that sending a CC message back on the same CC number
moves the physical LED ring (confirmed behavior in the reference Bitwig extension for
this exact hardware, `e16-controller-script/`, but not independently verified against
Ableton).

## Architecture

Single Python package, `e16_ableton/`, installed into Ableton's
`~/Music/Ableton/User Library/Remote Scripts/` (or equivalent) folder:

- `__init__.py` — Ableton's entry point (`create_instance(c_instance)`), mirrors the
  Twister script's `__init__.py` pattern.
- `E16.py` (or similar) — the `ControlSurface` subclass. Hand-written directly against
  `_Framework`, not machine-generated — the Twister's generated file was 4,659 lines of
  boilerplate for a feature set this script doesn't need (banks, clip launching, session
  ring, arbitrary track offsets, sends, multiple modes). This script only needs:
  - `MixerComponent` (or a minimal custom subclass, following the Twister's
    `CustomMixerComponent` pattern if `tracks_to_use` needs overriding) sized to 16 tracks
  - 16 `EncoderElement`s (`MIDI_CC_TYPE`, channel 0, CC 1–16, absolute map mode) bound to
    each channel strip's volume control
  - 16 `ButtonElement`s (note type, channel 0, notes 0–15) bound to each channel strip's
    mute toggle

## Data flow

- Encoder turn → CC message in (channel 0, CC *n*, value 0–127) → `MixerComponent`
  channel strip *n-1* volume, mapped 0–127 → 0.0–1.0
- Push button → Note on (channel 0, note *n*) → toggle mute on channel strip *n*
- Ableton-side change (volume automation, mouse, undo, project load, track
  add/remove) → component's value listener fires → script sends CC *n* (volume) or
  Note on/off *n* (mute state) back out to the e16

## Error handling / edge cases

- Fewer than 16 tracks in the current set: `MixerComponent` leaves the corresponding
  channel strips unassigned; the relevant encoders/buttons are simply inert. No crash.
- e16 MIDI behavior differs from the spreadsheet in practice (wrong channel, note
  range, or the ring doesn't follow inbound CC as expected): treat this as the primary
  implementation risk. The plan should front-load a hardware smoke test — dump raw
  MIDI I/O for a few encoder turns and button presses — before wiring the full mixer
  logic, so any protocol mismatch is caught early and cheaply.

## Testing plan

No local Ableton/hardware access in this environment, so testing is manual,
user-driven, after each implementation milestone:

1. Raw MIDI smoke test: confirm encoder turns and button presses produce the expected
   CC/Note messages, on the expected channel, before any Ableton-specific code is trusted.
2. Install script, assign controller in Live 12 preferences, confirm Ableton recognizes
   it without errors in Live's log.
3. Per-encoder volume test: turn each of the 16 encoders, confirm the correct track's
   volume moves in Live, and confirm moving the same track's volume with the mouse
   updates that encoder's LED ring.
4. Per-button mute test: press each of the 16 push buttons, confirm the correct track
   mutes/unmutes, and confirm toggling mute from Live's UI updates the button LED.
5. Edge case: load a set with fewer than 16 tracks, confirm no errors and unused
   controls are inert.
